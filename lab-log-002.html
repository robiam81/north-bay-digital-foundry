When a CLI is the whole product

Most of what ends up on this site starts as a calculator: a formula, a form, an answer. The Fleet Maintenance Review Tool started differently — as a question about what an AI coding assistant can responsibly build when the subject is maintenance decisions on public equipment.

The premise was deliberately narrow. Fleet maintenance software gets sold with words like "predictive" and "AI-powered," and most of that is marketing wrapped around a set of if-then rules. So instead of pretending otherwise, I asked for the if-then rules — deterministic, documented, and configurable — and nothing more. A vehicle's service history and current readings go in; a plain-language explanation of what's current, due soon, overdue, or too undocumented to assess comes out, along with a review priority score. No claim of predicting failure. No claim about whether a vehicle is safe to drive. Those are still a person's call.

02 · The build

What "built with AI" actually looked like

This wasn't a single prompt producing a finished tool. It was three build passes and two independent review passes, each with a narrower job than the last:

  • Pass one built the architecture — ingestion, validation, rules, scoring, and reporting kept as separate layers, so a future statistical model could plug into the scoring layer without touching the rest.
  • Pass two turned a working prototype into something installable — a proper package, a --version flag, a placeholder-config banner so nobody mistakes the default intervals for real ones, and the first release build.
  • An independent review pass — a second AI, with no context from the first, given nothing but the code and told to try to break it — found two real defects. One let a careless command overwrite the very file it was reading. The other let a malformed spreadsheet row get silently truncated instead of rejected, meaning bad data could pass through undetected.
  • Pass three fixed both, plus six smaller issues the review also caught, and added a regression test for every one.
  • A second, narrower review then went after the fixes specifically — deliberately trying edge cases like symlinks, path casing, and multiple errors in one file — and found the fixes held.

03 · What it's for

What that process is actually for

None of this makes the tool "smart." It makes the tool honest about not being smart, and it catches the kind of bug a single confident build pass doesn't notice because it's checking its own work. The review that found the overwrite bug wasn't cautious because it was told to be — it was a different AI session with no stake in the first one being right, testing exactly the kind of careless command a tired person actually types.

The result is a prototype, and it's labeled as one everywhere it appears: in the terminal banner, in the exported reports, on this site. Its default maintenance intervals are placeholders, not real manufacturer schedules. It hasn't been run against a real fleet's data. What it offers instead is a specific, bounded kind of usefulness — a consistent first pass at "what needs a human's attention first" — built and checked with enough rigor that I'm comfortable putting my name on the download.
